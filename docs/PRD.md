## 1. 产品定位

**一句话定义**
把"说出来的内容"和"写下来的灵感"统一收纳的个人资产库：**随时快录 / 快记 → 自动转写 → 全文检索 → 回溯定位**。

**品牌与命名 `[已确认 D30]`**

| 项 | 内容 |
|---|---|
| 中文名 | **雁书** |
| 英文名（开源品牌） | **Gaggle** `[D40]` |
| Slogan | **把念头，寄给未来的自己** |
| 命名逻辑（中文） | 古有"雁足传书"——念头先被记下（录 / 写），再被寄出（交给 AI），最终寄达未来（理想达成）。名字本身即产品旅程 |
| 命名逻辑（英文） | Anser 是"雁属"，**gaggle 是"一群雁"的专用量词**（a gaggle of geese），同时有"七嘴八舌"之意——正好对应多人对话录音。中英两个名字指向同一个意象，不是两套品牌 |
| 弃用 Anser 的原因 | ① `anser` 检索冲突严重（雁属学名占满结果 + 知名 IR 库 Anserini）；② 英文用户易当成 answer 拼错；③ 名字本身不传达用途 |
| 资产与包名 | `gaggle.app` → `getgaggle.com`；GitHub 组织 `gaggle`；应用包名 `com.gaggle.app`；安装目录 `%LOCALAPPDATA%\Gaggle` |
| 品牌语气 | 沉稳、有出处、略带古意；不卖萌、不喊口号 |
| 视觉提示 | 雁、信封、飞行轨迹；主色墨青 + 暖金 |
| 命名作业 | 商标核查（WIPO + 中国商标网）、域名与社交账号抢注（发布前完成） |

**核心洞察**
- 灵感爆发时不一定能说话 → 必须同时支持"一键语音"与"一键文字"。
- 录音价值不在音频本身，而在"能被我重新找到" → **转写 + 检索定位是产品核心**。

**要解决的问题**
1. 灵感/会议内容散落在录音文件、备忘录里，事后找不回。
2. 长录音无法快速定位到"那句话在第几分钟"。
3. 电脑和手机上的记录互相割裂。

**非目标**
不做线上会议客户端 · 不做语音社交 · 不自研 ASR 模型 · 不做硬件 · 不做云端账号与后端（v1）
**不自建 LLM**：AI 能力一律通过对接用户本地的 Agent（A2A）获得，本体只负责组织语料与展示结果

**成功标准 `[假设]`**
- 按快捷键到开口说话 < 1 秒
- 想找一句话，3 秒内搜到并听到原声
- 连续使用 2 周不丢一条内容

## 4. 范围分层

### 4.1 MVP 功能清单

> 原则：**录 → 存 → 转 → 查 → 问（交给本地 Agent）** 这条路必须绝对可靠，其余一律延后。

| # | 功能 | 说明 |
|---|---|---|
| 1 | **快录** | 单麦克风；主界面按钮 + 全局快捷键；暂停/续录；实时电平与时长 |
| 2 | **速记** | 全局快捷键唤起轻量输入窗，纯文本，秒级保存 |
| 3 | **统一时间流** | 语音条目 + 文字条目同一列表倒序；重命名 / 删除 / 播放；每条显示**来源端**（电脑/手机/手表） |
| 4 | **转写** | 录音结束自动排队；带时间戳分段文本；硬件自动选档 |
| 5 | **检索跳转** | 搜索标题 / 速记正文 / 转写正文；**点击命中片段跳到对应时间点播放** |

| 7 | **可靠性** | 录制分段落盘、崩溃恢复、转写队列可续跑 |
| 8 | **基础设置** | 存储目录、模型档位、快捷键自定义、开机自启、打开数据目录 |
| 9 | **AI 对话（A2A）** | 自动发现本机 Agent；多选条目作上下文 → 提问 → 流式回答 → 多轮追问 → 会话留存。**手机端经电脑端中继调用同一 Agent（D38）** |
| 10 | **内容编辑** | 转写分段文本、速记正文、标题均可修改；保存后**重建该条目检索索引** |

### 4.2 MVP 明确不做

- ❌ 双轨录音（mic + system 分轨）→ 仍留 P1，作为"我/对方"场景的可选增强（D44）
- ❌ 实时转写、录制中打标记
- ❌ 音频裁剪编辑、格式转换、批量导出、字幕导出
- ❌ 项目/文件夹、收藏、高级筛选（标签已提前进 MVP，见 D57）
- ❌ 内置 AI 模型权重（模型一律走 Ollama / 云端 API / 本地 Agent，不随包分发）
- ❌ 一键生成会议纪要等固化流程（摘要仍由对话面板产出）
- ❌ 账号体系、云同步、团队共享
- ❌ 自动备份、云 ASR 实际接入（仅预留开关位）

### 4.3 P1（MVP 之后，按序推进）
1. **双轨录音**——与声纹互补：双轨判断"我/对方"准确率接近 100%，作可选增强（D44）
2. 项目分组 / 收藏 / 高级筛选（含**按说话人筛选**）；标签分组与标签云排序
3. 裁剪与片段导出、字幕导出（srt/txt，**带说话人前缀**）
4. 实时转写
5. 录制中打标记与快捷笔记
6. 云 ASR 实际接入
7. macOS 端
8. 自动备份到指定目录
9. AI 对话增强：回复存为独立笔记并关联来源、全库语义问答、一键生成会议纪要、多 Agent 编排

### 4.4 P2
穿戴设备 · iPhone · 录音笔直连 · 团队共享 · AI 自动打标与知识库沉淀

## 5. 界面与交互结构 `[已确认：D16]`

### 5.1 主窗口
- 布局：**左侧列表 + 右侧详情**（与已确认原型一致）
- 顶部：搜索框（全局搜索）、录制按钮、速记按钮
- 列表项：类型图标（语音/文字）、标题、创建时间、时长或字数、**来源端（电脑/手机/手表）**、转写状态（待转写/转写中/已完成/失败）
- 排序：创建时间倒序（MVP 唯一排序）

### 5.4 速记面板 `[已确认 D46：纯文字｜D52：全屏]`

### 5.11 同步状态与一键同步 `[已确认 D50 / D51]`

**每条内容的同步状态**

| 状态 | 触发条件 | 展示 |
|---|---|---|
| 已同步 | `uploaded_at` 非空（曾成功上传到电脑） | 绿色「已同步」 |
| 待同步 | 手机产生且从未上传 | 金色「待同步」 |
| 同步中 | 正在上传 | 蓝色 + 呼吸点「同步中」 |
| 重复 | 电脑端已存在相同内容哈希 | 灰底「重复」 |

- 电脑端自身产生的内容**不显示同步态**（本来就在电脑上）
- 同步状态与「来源端」「转写状态」并排显示，三者互不替代
- 状态语义是"曾成功上传过一次"，<u>不比对内容版本</u>；改了正文不会自动变回「待同步」

**一键同步**

- 位置：手机端时间流页顶栏右侧胶囊按钮，文案「同步」，右侧带待同步条数角标
- 点击：按顺序逐条上传，每条经历「同步中 → 已同步」过渡
- 结束：toast 汇总「已同步 N 条到电脑」，角标归零
- 无待同步内容时点击 → 提示「全部内容都已同步到电脑」
- 同步过程中按钮置灰、角标隐藏，防止重复触发
- 批量操作条另提供「重新上传」，可对**已同步**条目强制重传（用于电脑端数据丢失）

**验收**

- 手机录 3 条 → 列表显示 3 个「待同步」，角标显示 3
- 点一键同步 → 逐条变「同步中 → 已同步」，角标归零，电脑端对应出现 3 条且可回放
- 重复上传同一段音频 → 电脑端该条标记「重复」，并保留可继续导入的选择
- 电脑端自己录的条目 → 手机列表不出现「待同步」

## 6. 功能细则与验收标准

### 6.1 快录
- 入口：主界面按钮 + 全局快捷键 + 托盘
- 行为：按键即录（< 1s 内开始采集）；再按键停止并落盘；**暂停/继续**
- 实时反馈：悬浮条显示时长与电平
- 存储：AAC / m4a，`[待确认]` 采样率与码率（建议 16kHz 单声道对 ASR 足够，音质存档可用 44.1kHz/128kbps）
- 可靠性：按固定时长（如 30s）分段写入临时文件，停止时合并；崩溃/断电重启后检测未完成录音并提示恢复
- **验收**
  - 连续录 60 分钟不丢数据、不掉帧
  - 强杀进程后重启，能恢复已录部分
  - 从按键到开始采集 < 1 秒

### 6.2 速记
- 唤起：全局快捷键 → 输入窗（< 300ms 可输入）
- 保存：零等待写入本地，立刻出现在时间流顶部
- **纯文字，不录音**（D46）：不申请麦克风、不显示任何录音控件
- **验收**：不打断当前前台应用焦点切换体验；保存后立即可搜到；界面中不存在麦克风/波形/计时元素

### 6.3 统一时间流
- 字段：类型、标题、创建时间、时长/字数、转写状态
- 操作：播放、重命名、**编辑正文**、删除、多选
- **编辑规则 `[D31]`**：转写分段文本可逐段修改；速记正文可改；标题可改。保存后**同步重建该条目的检索索引**
- **删除规则 `[D32]`**：删除进回收站（保留 30 天，可恢复）；回收站内可「彻底删除」；列表删除后 10 秒内提供「撤销」
- **验收**：1 万条内容滚动流畅（虚拟列表）；改错字后原词搜不到、新词能搜到；误删 10 秒内可撤销

### 6.4 转写
- 触发：录音结束后自动入队（可设置为仅手动）
- 并发：单任务顺序处理，队列可暂停
- 输出：带时间戳分段文本（每段起止时间 + 文本 + **说话人**，见 6.13）
- 语言：中英混说
- 模型档位：启动检测 GPU/显存/内存自动选择，设置页可切换并提示速度与精度差异
- 状态机：`待转写 → 转写中 → 已完成 / 失败（可重试）`
- **未下载模型时**（原 5.9 规则，引导取消后归入本节）：录音 / 速记 / 检索照常可用，条目显示「待转写」；在设置页「转写」分组下载或导入模型后自动进入队列
- **音轨格式**：转写统一用 16kHz 单声道 PCM；录制的 m4a 与导入的其它格式都先转成这一中间态再喂给引擎
- 跨端：手机轻量模型结果可被电脑端重转并覆盖，保留旧文本备查 `[假设]`
- **验收**
  - 10 分钟中文（含英文术语）录音，转写文本可直接用于检索
  - 转写过程界面不卡顿，可继续录音与播放
  - 中断后重启，任务能继续或可一键重试

### 6.5 检索跳转
- 范围：标题、速记正文、转写正文
- 结果：命中条目 + 命中片段（含时间戳）+ 关键词高亮
- 交互：点击片段 → 播放器跳到该时间点并开始播放
- **验收**：搜"预算"，3 秒内出结果；点击后听到的正是包含该词的那段语音

### 6.6 局域网手动传输
- 前提：两端同 Wi-Fi，无需账号、不经服务器
- 流程 `[D50 修订]`：
  - **逐条**：手机条目上「上传到电脑」→ 立即上传 → 电脑端入库并转写 → 回写分段到手机
  - **批量**：顶栏「一键同步」→ 顺序上传全部「待同步」条目
  - 电脑端**不再弹确认框**（原"待接收列表 → 确认"已取消，改为静默入库 + 即时刷新；理由是两端口令后信任已由配对承担，多一步确认只会让人放弃同步）
- 发现：**UDP 广播自动发现**（端口 47821，已实现）；**配对码 + token 鉴权尚未实现**，当前局域网内同一 Wi-Fi 即可通信 `[待补 P0]`
- 去重 `[D56]`：按**音频内容哈希**判定，命中已有音频时给该条打「重复」标记，但不阻断入库与转写
- 已实现接口：`/ping`、`/agents`、`/probe`、`/transcribe`（音频）、`/note`（速记）、`/chat`（AI 中继）、`/a2a`（Agent 中继）
- **验收**：手机录一段 → 同 Wi-Fi 下电脑端 10 秒内可见、可播放、可被检索；手机列表该条由「待同步」变「已同步」

### 6.7 设置
- 存储根目录（可改，改后提示迁移）
- **「打开数据目录」按钮**（降低手动备份成本，D15 配套）
- 模型档位（自动/手动）
- **音频归档状态**：显示 `AAC · 已就绪` 或 `WAV · 缺 ffmpeg`，缺 ffmpeg 时说明「把 ffmpeg.exe 放进数据目录的 engine 文件夹即可启用 AAC」
- 快捷键自定义
- 开机自启
- 云转写开关（MVP 置灰并标注"即将支持"）

### 6.8 AI Agent 集成（A2A）`[已确认：纳入 MVP]`

**定位**
本软件不自建 LLM，定位为 **A2A Client**：把选中的多条录音/笔记组织成语料，交给用户本地运行的 Agent（A2A Server）分析；**结果直接回到软件内的 AI 对话面板**，可继续追问。所有 AI 能力（总结、问答、打标）共用这一条 Agent 通道。

**核心交互：AI 对话面板**
- 入口：主窗口「AI」按钮 / 列表多选后的「发给 AI」/ 托盘菜单
- 结构：左侧会话列表；右侧消息流 + 输入框
- 附加上下文：从多选进入对话时，所选条目以「引用卡片」形式显示在输入框上方（标题 + 时间 + 时长/字数），可增删
- 发送：提问 + 语料一并发出；回复**流式逐字显示**，可随时「停止生成」
- 多轮：同一会话内继续追问，复用 A2A `contextId` 维持上下文
- 持久化：会话与消息存本地，重开可继续；会话标题自动取首条提问
- 可追溯：每条回复可查看"本次引用了哪几条内容"，点击跳回原条目
- 默认首问模板 `[假设]`：`以下是 N 条录音/笔记的内容，请总结它们的核心观点、共同主题、分歧点与可执行的下一步。`

**Agent 自动发现（本版新增重点）**
A2A 规范本身**未定义**本机/局域网发现机制，需本软件自定义三层策略：

| 层 | 方式 | 说明 |
|---|---|---|
| L1 mDNS | 监听 `_a2a._tcp.local` 等广播 | 支持广播的 Agent 可秒级发现 |
| L2 本机端口探测 | 对 localhost 白名单端口 + 可配置端口段做 TCP 探测，命中后拉取 Agent Card 验证 | 覆盖面最广，主力手段 |
| L3 手动添加 | 用户填 Agent Card URL | 兜底，永远可用 |

- 探测策略 `[待确认]`：默认只扫「常见端口白名单 + 少量端口段」（数秒内出结果）；另提供「深度扫描」按钮扫全端口（慢，需用户主动触发）
- 认定标准：`GET /.well-known/agent-card.json`（旧版 `/.well-known/agent.json`）可解析才认定为 Agent `[待验证]`
- 展示：`Agent 名称 · 版本 · 协议版本 · skills 列表 · 在线状态`，由用户勾选启用
- 记忆：已发现的 Agent 落库，下次启动快速复检而非全量重扫

**请求构造（映射 A2A v1.0）**
- `Message.role = ROLE_USER`，`messageId = UUID`（幂等去重）
- `contextId`：同一会话复用，实现多轮
- `parts`
  - 1 个 `text`：用户提问 + 语料（每条含标题、时间、来源端、转写正文）
  - 可选 `data`：条目 ID 列表 / 时间范围 / 总时长，便于 Agent 精确引用
- **不发音频文件**（已确认，仅发转写文本）
- 结果读取：流式累积 `artifactUpdate`（`append` / `lastChunk`），终态以 `Artifact.parts` 为准
- 进度展示：消费 `statusUpdate`（SUBMITTED / WORKING / INPUT_REQUIRED / AUTH_REQUIRED）

**协议适配（关键风险）**
官方 v1.0 与 0.3 **不兼容**，需适配层，按 Agent Card 声明的 `protocolVersion` 自动选择：

| | v1.0 | 0.3 及更早 |
|---|---|---|
| 方法名 | `SendMessage` / `SendStreamingMessage` / `GetTask` / `CancelTask` | `message/send` / `message/stream` / `tasks/get` / `tasks/cancel` |
| 内容结构 | 单一 `Part` + OneOf（`text` / `raw` / `url` / `data`） | `TextPart` / `FilePart` / `DataPart` 具名类型 |
| 接口声明 | `supportedInterfaces[]`（含 `protocolBinding`、`protocolVersion`） | 顶层 `url` + `preferredTransport` |
| 传输 | `application/a2a+json`，请求头必带 `A2A-Version` | 同为 JSON-RPC 2.0，版本头可选 |

- 绑定：优先 JSON-RPC；若 Agent 仅提供 `HTTP+JSON` 则走 REST 端点
- 多 Agent：可保存多个配置并设默认，显示在线/离线状态
- 认证：本机优先无鉴权；若 Card 声明 `securitySchemes`，支持 API Key / Bearer Token `[假设]`

**异常与兜底**
- 找不到任何 Agent → 面板给出引导：「未发现本地 Agent，请启动它或手动添加地址」
- `FAILED` / `REJECTED` / `CANCELED` / 超时 → 消息气泡标红 + 可重试
- `INPUT_REQUIRED` → 直接在对话里继续回答（同 `taskId` + `contextId`）
- Agent 掉线 → 提示「连接已断开」，历史会话仍可查看
- 长语料超上下文 `[待确认]`：发送前估算并提示「已选 12 条，可能超出 Agent 上下文，建议分批」，可由用户强制发送或自动截断

**隐私**
- 只发给用户显式启用的本机 Agent；首次发送前确认「内容将发送至 <Agent 名称>（地址）」
- 仅发转写文本，不发音频
- 不做后台自动调用，不做任何联网上传

**MVP 边界 `[已确认：进 MVP]`**
- 做：Agent 自动发现 + 对话面板 + 多选引用上下文 + 流式输出 + 多轮追问 + 会话持久化
- 不做：定时汇总、自动打标、全库语义检索、多 Agent 编排、把回复存为独立笔记条目（P1）

**验收标准**
- 启动后 5 秒内自动发现本机正在运行的 A2A Agent，并显示名称、协议版本与 skills
- 选中 3 条录音 → 进入对话 → 提问 → 流式出字 → 可继续追问且上下文延续
- 关闭应用重开，历史会话与消息完整可见
- 未运行任何 Agent 时，录音 / 转写 / 检索完全不受影响

### 6.9 接入形态辨析：A2A（出站）vs MCP（入站）`[认识澄清]`

**常见疑问**："我在用的 CodeBuddy / Cursor 不就是智能体吗？为什么扫描不到？"

**答案**：它们是**宿主内嵌型 Agent**——运行在 IDE 进程内、由用户驱动、不对外暴露 Agent Card 与 JSON-RPC 端点，因此不符合 A2A 的 **Server** 角色，本软件既发现不了也调不动。

两个协议方向相反：

| | A2A | MCP |
|---|---|---|
| 方向 | Agent ↔ Agent（水平协作） | Agent → 工具/数据（垂直扩展） |
| 本软件角色 | **Client**（出站调用别人的 Agent） | **Server**（被别的 Agent 调用） |
| 对方要求 | 必须实现 A2A Server（Agent Card + 方法端点） | 必须支持挂载 MCP Server |
| 生态现状 | 本机可跑的实现较少 | IDE / 桌面 Agent 普遍支持 |
| 用户获得的价值 | 在软件内发起总结与多轮追问 | 在 CodeBuddy / Cursor / Claude 里直接问"我的录音说了什么" |

**可被 A2A 扫描到的**：只有专门启动了 A2A Server 的进程（官方 A2A SDK、Google ADK、自建服务等），**不包括** IDE 内置助手。

**结论 `[已确认 D26]`**：**不做 MCP 通道**，只保留 A2A 出站；AI 入口仅在软件内对话面板 `[D27]`。

**A2A 的 Agent 从哪来（现实约束）**
| 来源 | 可行性 | 说明 |
|---|---|---|
| CodeBuddy / Cursor 等 IDE 助手 | ❌ 不可行 | 无 A2A 端点，也无本地 API 可桥接，任何协议都调不到 |
| 用户自建 / 框架生成（A2A SDK、ADK、LangChain 等） | ✅ 可行 | 需用户自行部署并监听本机端口 |
| 软件附带的「参考 Agent」（可选启动） | ✅ 可行但**未采纳**（D28） | 独立小进程，发布标准 Agent Card，背后接本地模型或云 API |
| Mock Server（仅测试） | ✅ 可行 | 只验证协议链路，不产出真实总结 |

**Agent 供给 `[已确认 D28 / D29]`**
- 由**你自行部署**一个 A2A Server，软件**只做客户端，不附带 Agent 实现**
- 该 Agent 背后接**本地 Ollama**，全程离线，不产生额外费用
- 需要你后续提供：所用框架、监听地址/端口、协议版本（v1.0 或 0.3）
- 开发期用一个 **mock A2A Server** 验证协议链路（不进发布包）

> 若本地 Agent 未启动，对话面板显示"未发现 Agent"引导，但录音 / 转写 / 检索主链路不受影响。

### 6.9.1 手机端的 AI 能力从哪来 `[待确认 D38]`

手机上有两种截然不同的 AI，不能混为一谈：

| 类型 | 作用 | 手机能否本地运行 | 状态 |
|---|---|---|---|
| **转写模型（whisper）** | 语音 → 文字 | ✅ 能，量化小模型 150~190MB | 已定（D12） |
| **对话模型（LLM）** | 文字 → 总结/洞察 | ❌ 手机跑不动可用质量的 LLM | **待定，本节要解决** |

**物理约束**：电脑端 Ollama 常用的 7B 模型需 4~8GB 内存，手机即便勉强加载也极慢且严重发热；手机只能跑 1.5B~3B 量化模型，总结质量明显下降。

| 方案 | 体验 | 代价 | 评价 |
|---|---|---|---|
| **A. 手机经局域网连电脑上的 Agent** | 在家/办公室与电脑端一致 | 出门无网络即不可用，需提示"请连接电脑" | 与纯本地策略一致，零额外成本 |
| **B. 手机内置小模型（1.5B~3B）** | 随时随地可用 | 质量差、耗电发热、包体 +1~2GB、首次加载慢 | 适合只做"粗摘要" |
| **C. A + B 双通道** | 最好：优先连电脑，连不上用本地小模型 | 两套实现，工作量最大 | 适合作为 P1 目标 |
| **D. 手机端不做 AI 对话** | 移动端只负责录、记、转、查 | 移动端价值下降 | 最省工 |

**结论 `[已确认 D38：方案 A]`**：手机端**不自带对话模型**；同 Wi-Fi 下经**电脑端雁书中继**调用电脑上的 Agent。方案 C 列入 P1。

**为什么必须走中继（关键技术点）**
你的 A2A Server 大概率只监听 `127.0.0.1`（Ollama 默认如此），手机在局域网里**无法直连**。两种解法：

| 解法 | 说明 | 取舍 |
|---|---|---|
| 让 Agent 监听 `0.0.0.0` | 用户自行修改 Agent 配置 | 需懂网络配置，且把服务暴露到局域网有风险 |
| **由电脑端雁书做中继（采用）** | 电脑端监听局域网端口，收到手机请求后转发给本机 Agent | 用户零配置；需自行处理鉴权与转发 |

**中继流程**
```
手机端 →（UDP 发现电脑）→（配对码信任）→ POST /lan/chat（SSE 流）
       → 电脑端雁书 → 转发 127.0.0.1:<agent-port> → Agent
       → 流式回包 → 手机端逐字渲染
```

- `GET /lan/agents`：返回电脑端已发现并启用的 Agent 列表（名称 / 协议版本 / skills）
- `POST /lan/chat`：body = `{ items:[{title,text}], prompt, contextId }`，响应 SSE
- 鉴权：配对成功后下发 token，请求头必须携带；未配对一律 401
- 语料由**手机端拼好后上传**，Agent 无需访问手机数据；电脑端只做转发，不落盘对话内容（可选）

**限制与 UI 提示（必须做）**
- 电脑关机 / 休眠 / 雁书未启动 → 手机 AI 面板显示「未连接电脑」+ 一键重试
- 必须同一 Wi-Fi；跨网段、访客网络隔离会失败，需给出明确文案
- 手机 AI 面板顶部标注「经由 <电脑名> 的 Agent」，让用户清楚是电脑在思考

### 6.11 Android 平台适配 `[D35]` · **优先级 P0**

> 已确认（2026-11-21）：**手机需要支持 30 分钟以上会议录制**，因此本节三项必须落地，不降级为 P1/P2。

- 存储权限：使用分区存储（Scoped Storage），音频写入应用私有目录
- **验收**：息屏录制 30 分钟不中断；锁屏后通知栏可见录音状态

### 6.12 数据迁移与升级 `[D36]`
- 数据库带 `schema_version`，启动时自动执行迁移脚本（只前进不回退）

- **验收**：从 v1 数据库升级到 v2 后，原有条目、转写、会话全部可读

### 6.13 说话人区分（声纹分离）`[已确认 D43]`

**为什么不用双轨**：MVP 是单麦录音；双轨虽能天然区分"我/对方"，但需要单独做系统声音采集，且只在会议/通话场景有效。声纹方案对"导入的旧录音""手机录的音"同样有效，覆盖面更大。

**处理流程**
```
音频 → whisper 转写（得到带时间戳的分段）
     → 语音活动检测（VAD）切出语音段
     → 每段提取声纹 embedding（声纹模型）
     → 聚类（余弦距离 + 阈值）→ 得到「说话人1/2/3」
     → 按时间重叠把说话人标签回填到每个转写分段
     → 合并相邻同人分段，输出「说话人 + 文本 + 起止时间」
```

**产品交互**
- 转写文本每条前面显示**说话人标签**（带颜色区分），默认命名「说话人1/2/3」
- 转写区上方显示**说话人条**：列出本次识别到的所有说话人（人数、发言时长占比）
- 点击标签可**就地改名**（如「说话人1」→「李工」），该条目的所有同人分段同步更新
- 支持**合并**两个说话人（识别过度切分时）、**拆出**某段（识别错了）
- 说话人区分结果**随条目保存**，重开不变；用户手动修正后标记为「已校正」，不再被自动重算覆盖

**准确率预期（写进帮助文档，管理用户预期）**

| 条件 | 预期准确率 |
|---|---|
| 2 人清晰对话、不重叠 | 85% ~ 92% |
| 3~4 人会议、少量重叠 | 70% ~ 82% |
| 多人抢话、频繁插话 | 55% ~ 70% |
| 音色相近（同性同年龄） | 明显下降，建议手动修正 |

- **只能区分"A/B/C"，不能判断"是谁"** —— 必须靠用户重命名，产品不做声纹库注册（涉及隐私）
- 短段落（< 1 秒）与重叠说话是主要出错场景

**验收标准**
- 2 人对话样本，人工抽检 50 段，说话人归属正确率 ≥ 85%
- 3 人会议样本，正确率 ≥ 70%
- 声纹处理额外耗时 ≤ 转写耗时的 30%
- 改名后全条目同步更新，重开应用仍保留
- 无语音/纯音乐录音不产生虚假说话人（说话人数为 0 或 1）

### 6.14 批量操作规范 `[已确认 D39]`

条目与会话**共用同一套交互规则**，避免每处各写一套。

**进入多选**
| 端 | 方式 |
|---|---|
| 桌面 | 工具条「多选」按钮；`Ctrl`+点击多选、`Shift`+点击连选、`Ctrl+A` 全选、拖拽框选 |
| 手机 | 长按卡片 450ms 自动进入并选中该条；或点「多选」标签 |

**选中态**：行首出现勾选框；点击行 = 勾选/取消（不打开详情）；`Esc` 或「取消」退出。

**操作条**：在所属容器底部浮出，显示「已选 N」，只放合法操作。

| 对象 | 可用操作 |
|---|---|
| 条目 | 发给 AI、删除（进回收站）、发送到设备 |
| 会话 | 删除（**不进回收站**，直接生效） |

**规则**
- 操作完成后自动退出多选；切换视图/标签时重置选择
- 会话批量删除需二次确认；单条删除直接生效并提示
- 一次「发给 AI」的引用条目上限 **20 条**，超出提示分批

### 6.15 音频文件导入（电脑端）`[已确认 D45]`

**入口**
- 顶栏「导入音频」按钮
- 拖拽文件到主窗口任意位置（拖拽时高亮提示「松开导入」）
- 空列表时显示引导「或导入一个已有录音文件」

**支持格式**

| 类型 | 扩展名 |
|---|---|
| 音频 | m4a / aac / mp3 / wav / flac / ogg / opus / amr |
| 视频（仅取音轨） | mp4 / mov / mkv / avi |

**处理流程**
```
选择/拖入文件 → 校验格式与大小 → 提取音轨（视频转音频）
             → 重采样为 16kHz 单声道供转写
             → 生成条目（来源=电脑，标题=文件名，状态=待转写）
             → 进入转写队列 → 跑说话人区分
```

**规则**
- 支持**多选批量导入**；按顺序排队，不并发解码
- 单个文件上限 **2GB**
- 时长读取失败时显示 `--:--`，不阻塞导入
- 重复导入同一文件：按内容哈希判重，提示「该音频已存在」并允许强制导入
- 失败处理：格式不支持 → 明确提示支持的格式列表；解码失败 → 标记「导入失败」可重试
- 导入的条目与录制条目**完全等价**（可播放、可检索、可区分说话人、可导出）

**验收**
- 导入 1 个 30 分钟的 m4a，10 秒内出现在列表并开始转写
- 导入 mp4 视频，只提取音轨，进度可见
- 拖入不支持的文件，给出明确原因而不是静默失败

**确认弹窗规范**
- 标题写动作与数量：`删除 3 个会话？`
- 正文必须说明**后果边界**：`会话记录删除后不可恢复。其中的录音与笔记不会被删除。`
- 主按钮用危险色，文案与标题动作一致（删除 / 清空）；次按钮为「取消」
- 桌面与手机各自在所属容器内弹层，样式统一

## 7. 数据模型（草案）

**存储结构（与当前代码一致）**
```
<数据目录>/
  db/gaggle.db            # SQLite（元数据 + 转写 + 全文索引 + AI 会话）
  audio/yyyy/MM/<id>.m4a  # 录音最终形态：AAC / 44.1kHz / 单声道（D14）
  audio/yyyy/MM/<id>.wav  # 录制期临时文件，停止后转码为 m4a 并删除
  audio/*.pcm             # 转写用的 16k 单声道中间态，转写完即删
  audio/up_<ts>.wav       # 手机上传落盘
  models/                 # whisper 档位模型 ggml-*.bin
  models/diarization/     # 声纹模型 + diarizer.exe
  models/sensevoice/      # 手机端 SenseVoice 模型
  tmp/                    # 导入与传输临时文件
```
> 数据目录默认 `getApplicationSupportDirectory()/Gaggle`，可由配置目录下的 `location.json` 覆盖（设置页可改并迁移）。

**实际表（以代码为准，勿照旧草案开发）**

| 表 | 关键字段 | 说明 |
|---|---|---|
| **item** | id, type(audio/text), title, created_at, updated_at, source_device(pc/phone/watch), duration_ms, char_count, transcript_status, **audio_path**, **body**, deleted_at, **uploaded_at**, **dup_of**, **audio_hash** | 音文合并为一张表；`body` 存速记正文；`uploaded_at` 非空 = 已同步过 |
| **transcript_segment** | id, item_id, seq, start_ms, end_ms, text, **speaker_id**, confidence | `speaker_id` 存的是**说话人名**，不是外键 |
| **item_tag** | item_id, tag, source(manual/ai) | 标签双来源，AI 只覆盖自己的标 |
| **ai_conversation** | id, agent_id, a2a_context_id, title, created_at, updated_at | |
| **ai_message** | id, conversation_id, role(user/agent), content, source_item_ids(JSON), state, created_at | |
| **ai_conv_ref** | conversation_id, item_id | 会话 ↔ 条目引用 |
| **ai_message_ref** | message_id, item_id | 单条回复 ↔ 条目引用 |
| **setting** | key, value | 全局键值：`ai_provider` / `ai_base_url` / `ai_model` / `ai_api_key` / `ai_auto_name` / `ai_auto_tag` / `a2a_selected` / `a2a_manual` / `model_tier` / `close_action` / `transcribe_on` |
| **search_idx** | FTS5(content, item_id, tokenize=trigram) | 覆盖标题 / 正文 / 分段 / 标签 |

**与原草案的差异（重要）**

- `audio_file` / `text_note` / `speaker` / `asr_job` / `device` / `transfer_log` / `agent_config` / `a2a_task` **均未建**：
  音频路径与哈希并入 `item`；说话人名字直接存 `transcript_segment.speaker_id`；Agent 配置走 `setting` 表的 `a2a_*` 键
- **无 `schema_version`**：当前只做"缺列就 `ADD COLUMN`"的兼容，**无升级脚本、无迁移前备份**（与 D36 不符，待补 P1）
- **无 `transcript_model` 与历史快照**：换模型重转直接覆盖旧文本，"旧文本保留备查"未实现（与 D36 / 6.12 不符）

**搜索现状**

- FTS5 trigram 表已建，`rebuildIndex` 会写入标题 / 正文 / 分段 / 标签
- 但查询用的是 `WHERE content LIKE '%kw%'`，**不走 `MATCH`**，trigram 索引实际未生效
- 无命中片段与时间戳返回 → 桌面的"点击命中跳到时间点播放"因此无法实现（待补 P0）

**约定**

- 内容 ID 全局唯一（UUID），保证跨端不冲突
- 时间统一存 UTC，展示按本地时区
- 删除采用墓碑标记（`deleted_at`）；`uploaded_at` 语义为"曾成功上传过一次"，**不随内容修改失效**

## 11. 风险登记

| 风险 | 影响 | 应对 |
|---|---|---|
| **导入格式/编码千奇百怪** | 用户拖进来的文件打不开 | 明确支持列表；失败给出具体原因；解码走 FFmpeg 兜底 |
| **导入超大文件（2GB+、数小时）** | 内存爆或转写跑几小时 | 流式解码；上限 2GB；超长分段转写并提示预计耗时 |
| **声纹分离准确率有限**（重叠说话、短句、音色相近时更差） | 会议记录不可信，用户不再用 | 明确预期表；支持手动改名/合并/拆出；双轨作 P1 增强 |
| **声纹增加转写耗时** | 10 分钟录音多等 2~3 分钟 | embedding 只在语音段上算；可在设置中关闭说话人区分 |
| 声纹误判导致检索失真 | 按说话人筛选结果错误 | 允许手动校正，校正后标记「已校正」，不随重转覆盖 |
| MVP 无双轨，会议场景音质差 | 声纹在糊音频上更不准 | 定位为过渡态，双轨仍列 P1 第一项 |
| 大模型在无 GPU 电脑上过慢 | 转写等待数分钟至十几分钟 | 自动检测选档 + 后台队列 + 进度提示 + 手动切档 |
| 安卓跑大模型不可行 | 与"离线也能转"预期冲突 | 手机固定轻量模型 + 回传电脑重转 |
| **纯本地无备份，硬盘损坏全丢** | 数据不可恢复 | 已确认由你手动拷目录；提供「打开数据目录」入口；P1 补自动备份 |
| **内容未加密** | 电脑被他人使用时可被读取 | 已确认 MVP 不做加密；依赖系统盘加密 + 系统账户隔离；后续可加库加密 |
| 本地模型体积大 | 安装包大、分发难 | 建议首次使用时下载 |
| 蓝牙耳机/不同声卡采集兼容性 | 录不到或音质差 | M1 内做多设备实测 |
| 局域网传输断连 | 大文件传一半失败 | 断点续传 + 进度提示 |
| AAC 有损压缩影响后续重转写 | 换模型收益受限 | 128kbps 对识别影响可忽略，可接受 |
| 双端并行开发资源分散 | 两端都做不深 | 先 Windows 打通，Android 复用数据模型与协议 |
| 无账号下设备信任 | 传错设备/被蹭 | 配对码 + 设备白名单 |
| **电脑休眠/关机时手机 AI 不可用** | 移动端 AI 面板空转 | 明确「未连接电脑」状态 + 一键重试；本地录音/转写/检索不受影响 |
| **中继端口暴露到局域网** | 同网段他人可能调用 Agent | 必须配对后方可调用（token 鉴权）+ 可一键关闭中继 |
| **A2A 协议版本分裂（v1.0 vs 0.3 不兼容）** | 对接不同 Agent 需双实现 | 做协议适配层，优先支持你实际使用的版本 |
| **本地语料超出 Agent 上下文窗口** | 跨条总结丢内容或直接报错 | 分批摘要再汇总 / 限制单次条数与字数 |
| Agent 未运行时 AI 功能不可用 | 用户误以为软件故障 | 明确"未连接"状态，主链路完全独立 |
| 多选 + 网络通信抬高 MVP 复杂度 | 主链路交付被拖延 | 已确认进 MVP；M0 阶段先做 A2A 连通性验证，避免后期返工 |
| AI 结果质量不可控 | 总结失真、误导用户 | 结果标注"由 AI 生成"与所用 Agent/模型，保留原始语料可回溯 |
| **本机 Agent 自动发现不可靠** | 扫不到 Agent，用户以为功能坏了 | 三层发现 + 手动 URL 兜底 + 明确引导文案；A2A 无标准发现机制，需自建约定 |
| 端口探测触发安全软件告警 | 被拦截或误报 | 默认只扫白名单端口，深度扫描需用户主动触发并说明用途 |
| **没有可用的 A2A Agent（CodeBuddy 无法充当）** | "问"功能上线即空转，M4 无法交付 | M0 阶段先定 Agent 供给方式：附带参考 Agent 或用户自建 |
